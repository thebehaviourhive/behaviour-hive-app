# Supabase / Postgres gotchas

Learned the hard way, on the School Incident Log build. Read before writing any code that touches RLS.

- **RLS on UPDATE silently filters, it doesn't error.** A `.update()` whose target row fails the policy's USING clause returns `{ data: [], error: null }` — no thrown error, no signal at all. Never trust the absence of a client-visible error as proof a write succeeded, or that a negative test correctly blocked something. Re-read the actual persisted state afterward via a privileged (service-role) query.

- **Chaining `.select()` onto `.insert()` requires the new row to pass the table's SELECT policy WITHIN THE SAME STATEMENT** (PostgREST sends `Prefer: return=representation`). If a row's visibility depends on related rows that don't exist yet in that same transaction — e.g. an incident whose visibility partly depends on its children, inserted a moment later — the chained `.select()` can fail even though the bare insert, and a separate follow-up `.select()` afterward, both succeed. Don't work around this with a client-generated id (`crypto.randomUUID()`) to dodge the RETURNING clause; if the row's own existence should never be structurally possible without its children, fix it properly with a single atomic SECURITY DEFINER RPC that inserts everything in one transaction.

- **An embedded PostgREST join across a table with its own RLS returns EMPTY on the joined side, not an error.** `.select("incident_children(child_index, passports(child_name))")` silently drops the `passports` fields if the caller's session doesn't satisfy `passports`' own SELECT policy — even when the outer row (`incident_children`) is fully visible. The page renders wrong data (e.g. a name silently becomes "Unnamed child") with nothing failing anywhere to notice. When a relationship is deliberately broader than the joined table's own RLS — e.g. institution-roster-wide visibility that doesn't require the ordinary per-user grant (`passport_access`) — resolve it through a dedicated SECURITY DEFINER RPC instead of an embedded join. In this codebase: roster-scoped child names always resolve through `get_institution_child_roster()`, never a direct or embedded `passports(...)` read.

- **Whenever a migration changes behavior that existing adversarial checks depend on, re-audit those checks in the same session — and say so in the report.** A check can quietly become a no-op instead of failing: e.g. `get_parent_incidents()`'s gate changed from `status <> 'draft'` to `teacher_signed_at is not null`, which correctly made an existing check's row count go from 1 to 0 — but a *second* assertion right next to it read `row = rows?.[0]` and asserted a property was absent on that (now-undefined) row, which is vacuously true whether or not the property would actually leak. Nothing failed, so nothing flagged it; it was only caught by deliberately grepping for every place the changed function/table/column was referenced and reading each call site against the new behavior. Do that grep as a standing step after any migration that changes an existing function's gate, a table's shape, or a trigger's condition — not just when something conveniently fails first.

- **FIXTURES AND NEW LIFECYCLE STATE.** When a migration adds a state a production path is responsible for setting, existing fixtures WILL break — and that is correct. Fix them by driving the real production path (the RPC, as a real signed-in session), never by setting the column directly in a service-role insert. A fixture that sets such a column directly is testing the database's shape, not the system's behaviour. This happened for real when `0100_institution_join_approval.sql` made `class_teacher`/`sna` joins pending by default: every fixture across the suite that inserted staff via service role had encoded "row exists = active," correctly went false, and 353 checks failed loudly rather than passing against a state production no longer produces — the opposite outcome to the earlier `status: "awaiting_attestation"` incident (a fixture hand-setting a column production derives, which stayed green while masking a real bug through 180 checks), from the identical root cause. The fix in both cases is the same: call the real RPC (`approve_staff_join()`, as the principal's own session), never assign the column. One more thing worth naming from this repair pass: fixing ~6 fixture blocks this way exercised `approve_staff_join()`'s happy path repeatedly as a side effect, but not one existing check asserts on that RPC's *own* correctness (authorization, refusing a non-principal or wrong-institution caller, refusing double-approval) — every downstream check only needed the state it produces to be right, not the RPC's own behavior verified. That verification doesn't exist yet anywhere in the suite; a fixture-repair pass fixing fixtures is not the same claim as Step 2 writing real coverage for a migration's own new surface, and shouldn't be mistaken for it.

- **The adversarial suite tests the database, not the journey — it never renders or drives a UI.** Every check calls the Supabase client directly with a real JWT; none of them touch a React component, a redirect, or conditional rendering. A check whose NAME describes a user-facing outcome ("a deactivated person rejoining...") can pass while the actual page a person uses is broken, if the bug lives entirely in client-side routing/gating logic rather than in RLS/an RPC/a trigger — the class of thing this suite is built to catch. This happened for real: `join-institution/page.tsx`'s `checkExisting()` had no `deactivated_at` filter, silently redirecting a deactivated person back to their old dashboard instead of the join form, while CHECK V10's own direct-INSERT check kept passing, honestly proving the database would accept a legitimate rejoin — a true claim, just narrower than the check's name promised. Found only by hand, not by the suite. When a check's claim is about what a user would *experience* rather than what the database *permits*, write it against the CLIENT'S OWN QUERY SHAPE, file:line-matched to the component that gates the real journey — not a proxy for it, the literal same filter — so a regression in that client code fails the check the same way a regression in an RLS policy would.

- **COVERAGE GAPS ARE NOT WRONG-REASON PASSES.** A wrong-reason pass is a check that asserts the wrong thing. A coverage gap is a mechanism with no check at all, exercised only as a side effect of other fixtures. `approve_staff_join()` had six fixtures depending on its happy path and zero checks on its guards. When a new RPC is added, ask what asserts its REFUSALS — not whether anything uses it.

# Verification environment

- **Browser verification runs against the DEPLOYED app** — `.claude/launch.json`'s `deployed` entry (`https://behaviour-hive-app.vercel.app`), not `local-dev`. A local dev-server check exercises real RLS against the real Supabase project, which is genuinely useful, but it does not prove the deployed build behaves the same — different bundle, different environment. **State which environment was actually used in every report, every time** — the same way the deployed commit SHA gets stated, not left implied. "Verified live" with no environment named is not a real claim; it's the gap that let browser verification run against `local-dev` for two straight days (Aug 25–27) while every report during that window said "verified live" and meant local. Caught only when asked directly, not by anything failing.

# Deferred work

- **STRUCTURAL-ONLY CHECKS, STAGE 1.** Five call sites protecting a currently-unreachable state — `deactivate_institution_staff()`'s last-principal guard, `can_countersign_incident()`'s principal branch, `incident_locations` add/edit principal branches, `mark_parent_called()`, and (added during Stage 1b) `approve_staff_join()`/`reject_staff_join()`'s caller check together with `derive_staff_join_approval()`'s EXISTS clause — specifically the claim that a *pending or rejected* principal doesn't count as active. All five are structural exhibits, not live-fired, because no principal can currently be deactivated, and a second principal-role row at an institution that already has one can't exist in ANY state, pending or rejected — `institution_staff_one_principal_per_institution` is keyed on `role='principal' and deactivated_at is null and rejected_at is null`, so the INSERT itself fails at the unique index before a row can persist. Confirmed empirically, not just reasoned: a second principal-role insert at an institution with an active principal returns `duplicate key value violates unique constraint` even via a service-role client, and this happens whether or not the auto-approve trigger would have left it pending — the row never exists to check. Stage 1b (principal handover) makes this state reachable. WHEN IT SHIPS, convert all five to live-fired checks using a genuinely handed-over, deactivated principal.

- **SECOND-PRINCIPAL JOIN: A DESIGN GAP, NOT JUST A TEST GAP.** The finding above has a second half beyond test coverage: today, a second principal-role join attempt at an institution that already has one surfaces a raw `duplicate key value violates unique constraint "institution_staff_one_principal_per_institution"` to whatever caller triggers it — not a designed message, not a pending state, just a database error. This is in scope for Stage 1c's build prompt, not deferred alongside the structural checks above: the person hitting this is very likely the successor in a real handover, and the fix is a designed message pointing them at handover (ask the current principal to do it / contact support), not a friendlier pending state — a second principal was never meant to queue.
