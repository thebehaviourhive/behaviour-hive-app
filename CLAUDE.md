# Supabase / Postgres gotchas

Learned the hard way, on the School Incident Log build. Read before writing any code that touches RLS.

- **RLS on UPDATE silently filters, it doesn't error.** A `.update()` whose target row fails the policy's USING clause returns `{ data: [], error: null }` — no thrown error, no signal at all. Never trust the absence of a client-visible error as proof a write succeeded, or that a negative test correctly blocked something. Re-read the actual persisted state afterward via a privileged (service-role) query.

- **A STALE SNAPSHOT LOOKS EXACTLY LIKE A FAILED WRITE.** `SignOffCard` fetched `get_incident_signoff_summary()` once on mount, keyed on `incidentId`. A teacher answered a question, the write succeeded and persisted, and the card kept reporting "not recorded" from before the answer. Diagnosed twice as a write bug — once correctly for a different cause, once wrongly. When a summary or derived view disagrees with the database, check WHEN it was read before checking whether the write landed.

  **Second confirmed instance, same session, worse presentation:** `CountersignCard`'s own `summary` had the identical shape — fetched once, keyed on `[incidentId]` alone, no refresh signal from its own successful action. A real countersign wrote `countersigned_at`/`countersigned_by` correctly (confirmed directly against the database), the sheet closed, and the card kept rendering "Countersign record" — not a stale VALUE this time, a stale ABSENCE OF ANY VISIBLE CHANGE AT ALL, which reads as "nothing happened" far more convincingly than a stale field ever could. Reported live as "no confirmation appeared" — the confirmation genuinely had appeared and the action had genuinely succeeded; the screen afterward just looked identical to before, with nothing to signal otherwise. `SignOffCard`'s own equivalent bug never surfaced this way only because `isLocked` flips true on success and unmounts the whole component — a coincidence of that specific card's gating, not a property of the fix. `AddAmendmentSheet`'s own `onAdded` callback, three lines below the bug in the exact same file, already had the correct fix (`applyCountersignData(await fetchCountersignData())`) for a different action on the same component — the working pattern was present and simply wasn't applied to the action that needed it most. When any card owns its own derived summary AND its own mutating action, the action's own success handler must refresh that SAME local state directly — never assume a parent's refetch (`reloadKey`, a prop bump) will reach a component that isn't unmounted/remounted by it.

  **AND IT WAS DISMISSED ONCE AS A TOOLING QUIRK.** The CountersignCard instance was seen during live verification, attributed to a browser click not landing, and closed. The action had succeeded and the card rendered unchanged. When a live check produces "the click did not seem to work" but the database shows the write landed, that is a stale read, not a tooling problem — check the component's own refetch before blaming the browser.

- **A WRITE BEFORE A RAISE DOES NOT SURVIVE.** An uncaught exception rolls back the whole transaction the RPC runs in, including any insert or update earlier in the same function. `redeem_passport_claim_code()` recorded a rate-limit failure and then raised — so the limiter recorded nothing at all from the day it shipped. If a function needs to record something AND refuse, it must return rather than raise, or record in a separate transaction. This is not obvious from reading the function — it reads as though the insert lands and then the caller errors. Found by a targeted one-sign-in diagnostic (12 wrong-code attempts, `code_lookup_attempts` stayed at 0 rows every time), not by code review; fixed in migration 0116 by matching `lookup_passport_by_code()`'s own original pattern (0034) — `insert ...; return;` for the case that needs to record and fail, a normal zero-row return instead of an exception.

  The rule alone over-triggers — a schema-wide audit immediately after this fix found three OTHER functions with the identical textual shape (write, then later a raise) that are correctly written, not the same bug: `send_message()`, `create_incident_stamp()`, and `generate_passport_claim_code()`. In each, the write is part of the entity being atomically constructed — a message, an incident stamp, a code reissue — and rolling it back on failure (no valid recipients, an unlinked child, ten random-code collisions) is the correct behavior, not a silent loss. The actual bug class is narrower: a write to a table whose entire JOB is to survive the call's own failure — an audit log, an attempt counter, a rate limiter. `code_lookup_attempts` is currently the only such table in this schema. Audit any function that writes then raises against that distinction specifically, not the bare textual pattern — without it, the next audit produces false alarms and someone "fixes" correct atomicity.

- **Chaining `.select()` onto `.insert()` requires the new row to pass the table's SELECT policy WITHIN THE SAME STATEMENT** (PostgREST sends `Prefer: return=representation`). If a row's visibility depends on related rows that don't exist yet in that same transaction — e.g. an incident whose visibility partly depends on its children, inserted a moment later — the chained `.select()` can fail even though the bare insert, and a separate follow-up `.select()` afterward, both succeed. Don't work around this with a client-generated id (`crypto.randomUUID()`) to dodge the RETURNING clause; if the row's own existence should never be structurally possible without its children, fix it properly with a single atomic SECURITY DEFINER RPC that inserts everything in one transaction.

- **`.upsert()` TRIGGERS THE SELECT POLICY IMPLICITLY.** supabase-js sends `Prefer: return=representation` on `.upsert()` by default even with no `.select()` chained, so the new row must pass the SELECT policy within the same statement. Gotcha #3 above describes this for `.select()` chained onto `.insert()`; `.upsert()` does it invisibly, with nothing in the source to make it obvious. 0117 rewrote `passports`' SELECT policy to `owns_passport()` and silently broke every first-time passport creation, because the guardian row a trigger creates after the insert is not visible to the representation check in the same statement — live in production from the moment 0117 shipped until PRD 3 Stage 1 found it by accident, debugging an unrelated check. Not a claimed-guardian edge case: every brand-new parent's very first save, on both `/passport/welcome` and `/passport/section-a`. When changing ANY table's SELECT policy, grep for `.upsert()` against that table.

- **`CREATE OR REPLACE FUNCTION` DOES NOT COLLAPSE A LONGER PARAMETER LIST ONTO A SHORTER ONE — IT CREATES A SECOND, SILENT OVERLOAD.** Adding a new trailing parameter (even with a default) via bare `CREATE OR REPLACE` does not replace the existing function; Postgres keeps both signatures as independent overloads. `send_message()` did this twice — 0062 added `p_abc_log_id`/`p_strategy_update` without dropping 0061's 5-param original, and 0168 (staff-to-staff messaging) repeated the identical mistake adding `p_institution_id`, explicitly citing 0161 as a safe precedent for the pattern. That precedent was never actually safe — it just had never been tested by a caller that omits the newest parameter, because every real client call site in this codebase has always passed every parameter explicitly. It surfaced immediately the first time CHECK NNN called `send_message` with a narrower, realistic parameter set: `Could not choose the best candidate function between: send_message(...7 params), send_message(...8 params)`. Fixed in 0169 by dropping every historical signature explicitly, then creating the function fresh, exactly once — the same shape this codebase already gets right everywhere else: `get_institution_incidents` (0166), `get_institution_staff_roster` (0097, then again 0100), and `revoke_passport_claim_code` (0126) each grew a parameter at some point, and every one of them correctly did `drop function if exists ...(old signature); create function ...` first, confirmed by reading each one directly, not assumed. `send_message` was the only function in the schema that skipped that step. **The actual rule, corrected: a new trailing defaulted parameter is NEVER safe to add via bare `CREATE OR REPLACE` — always `DROP FUNCTION IF EXISTS` for every prior signature first, then `CREATE FUNCTION`, with no exception for "it's just one optional param."** When touching any function whose parameter list has grown before, grep its own migration history first (same function name, differing parameter counts) rather than trusting the most recent comment's own claim that CREATE OR REPLACE was sufficient — that claim itself can be wrong and uncaught, exactly as it was here.

- **A REBUILD CAN SILENTLY DROP A GATE AND CLAIM IT DID NOT.** `0060` replaced `fba_afls_data` with `afls_assessments` and its own header comment says "same gate `fba_afls_data` always used". True for the parent-read policy, false for all three clinician write policies — the completed-FBA lock was lost. It went unnoticed for months and a real post-lock write occurred (see the dedicated Stage 8 entry under "Deferred work" for the full incident). When a migration replaces a table, diff the OLD table's policies against the new ones explicitly rather than trusting the migration's own account of itself.

- **A TYPESCRIPT INTERFACE NARROWER THAN THE RPC IT TYPES IS INVISIBLE — THE DATA READS AS ABSENT, NOT UNDECLARED.** `build_staff_attestations_summary()` has returned `withdrawn_at`/`withdrawal_reason` for every staff row since 0149, regardless of current status — a real, working, already-shipped signal. `SignOffCard.tsx`'s own `StaffAttestation` interface only ever declared `incident_staff_id`/`name`/`has_account`/`status`/`status_label`/`blocks_signoff`. The two fields sat in every API response, unused, for weeks — not because the data was missing, but because nothing in the type declared it, so nothing in the component ever looked. Found while building the sign-off confirm-sheet rework, not by anyone deliberately auditing this gap. When a client interface types an RPC's `jsonb`/`json` return, treat a narrower interface as a standing question — check the RPC's own `jsonb_build_object` (or equivalent) for fields the interface dropped — rather than assuming "not in the type" means "not in the response."

- **A FIXTURE THAT REUSES AN ACCOUNT TESTS THE SECOND CALL, NOT THE FIRST.** When a policy or check depends on a row a trigger creates in the same statement, the first-ever invocation is a different code path — visibility depends on something that does not exist yet. 0117 rewrote `passports`' SELECT policy to `owns_passport()` and broke every first-time passport creation for weeks, invisibly, because every fixture already had a passport row. When a policy references a trigger-populated row, that function's first invocation needs its own dedicated fixture. Not a blanket instruction to use fresh accounts — the precondition is the trigger dependency.

- **HOME LOGS REACH THE CLASSROOM BY DESIGN, VIA THE CLINICIAN.** A parent's home ABC entry is invisible to school staff. A clinician with active access reads the full home history, and `approve_fba_strategies()` publishes what they choose into `passport_clinical_content` as `strategy_school` / `strategy_shared` / `trigger` / `setting_event` — all school-visible. `strategy_home` is deliberately excluded. The raw log never crosses; the clinical interpretation does. This is shipped and working. Do not treat the home/school boundary as a dead end and build a route around it.

- **An embedded PostgREST join across a table with its own RLS returns EMPTY on the joined side, not an error.** `.select("incident_children(child_index, passports(child_name))")` silently drops the `passports` fields if the caller's session doesn't satisfy `passports`' own SELECT policy — even when the outer row (`incident_children`) is fully visible. The page renders wrong data (e.g. a name silently becomes "Unnamed child") with nothing failing anywhere to notice. When a relationship is deliberately broader than the joined table's own RLS — e.g. institution-roster-wide visibility that doesn't require the ordinary per-user grant (`passport_access`) — resolve it through a dedicated SECURITY DEFINER RPC instead of an embedded join. In this codebase: roster-scoped child names always resolve through `get_institution_child_roster()`, never a direct or embedded `passports(...)` read.

- **Whenever a migration changes behavior that existing adversarial checks depend on, re-audit those checks in the same session — and say so in the report.** A check can quietly become a no-op instead of failing: e.g. `get_parent_incidents()`'s gate changed from `status <> 'draft'` to `teacher_signed_at is not null`, which correctly made an existing check's row count go from 1 to 0 — but a *second* assertion right next to it read `row = rows?.[0]` and asserted a property was absent on that (now-undefined) row, which is vacuously true whether or not the property would actually leak. Nothing failed, so nothing flagged it; it was only caught by deliberately grepping for every place the changed function/table/column was referenced and reading each call site against the new behavior. Do that grep as a standing step after any migration that changes an existing function's gate, a table's shape, or a trigger's condition — not just when something conveniently fails first.

- **WHEN A FUNCTION'S RETURN CONTRACT CHANGES, UPDATE ITS CALLERS IN THE SAME PASS.** `0113` changed `get_child_clinical_document_status()` to always return one row with an `is_authorized` flag, instead of zero rows for "no document yet." Its own comment warned future callers to check `is_authorized` explicitly; the two EXISTING callers (`ClinicalSupportSection.tsx`, `CalmUnlockSheet.tsx`) were never updated, and every FBA-less passport showed "FBA complete" linking to `/passport/fba/null` — live from the moment 0113 shipped until Stage 5 Step 3 found it by chance, walking a genuinely fresh passport end-to-end. A comment protects readers, not code. Changing a `RETURNS TABLE` shape means grepping every consumer in the same migration, not just documenting the new contract for whoever writes the next one.

- **READ THE LIVE DEFINITION, NOT THE FIRST ONE YOU FIND.** A policy or function may have been altered several times. `0069`'s incident-edit policy genuinely lacked a `deactivated_at` check; `0105`/`0106`/`0107` superseded it and the current definition is correct. Flagging the historical version as a live gap wastes a fix and, worse, could produce one that reverts a later correction. Always resolve to the highest-numbered definition before concluding anything.

- **NINE INDEPENDENT LINEAGES CHECK `institution_staff` MEMBERSHIP, plus ~20 hand-written raw checks in individual RPCs.** The correct ones are correct by accumulated diligence, not by any enforced mechanism — `institution_staff_has_current_standing()` (0105) exists for exactly this and was used in one place until `0119`. Any NEW code checking `institution_staff` membership calls that helper. Never hand-write the `deactivated_at`/`approved_at` conditions again — it has been got wrong three times, including twice on the same policy across two dedicated fix passes (`passport_institution_links`' teacher-view policy, 0035 and 0112, neither of which was reading for this).

- **A COLUMN NAME IS A CLAIM. IF NOTHING WRITES IT TRUE FOR THE REASON ITS NAME SAYS, THE CLAIM IS FALSE.** `passport_institution_links.approved_by_parent` was a genuine consent record when it had exactly one writer: a parent, approving a school by code. PRD 3 Stage 2 removed that writer (`ShareBottomSheet`'s `handleApprove()`) as part of the school-led pivot, but `create_school_passport()` still sets it `true` on every school-created child — correctly, since a school creating its own child's record has no parent to seek approval from, and the flag is what keeps that link visible to gates written when it meant something else. The column is now a COMPATIBILITY DEFAULT, not a consent record, for every row it produces. Left un-commented, `approved_by_parent = true` on a school-created passport reads as evidence a parent approved something — which would be false, and is exactly the kind of thing that gets cited in a subject access request or a DPA review. Commented directly in `create_school_passport()` (0140) for this reason: harmless while everyone building on this schema knows why, dangerous the moment someone reads it at face value without that context. The general lesson: when a column's own name stops matching what actually causes it to be set, comment the write site, don't just remember it.

- **DEAD RLS POLICIES DON'T ANNOUNCE THEMSELVES — NAME THEM WHEN THE LAST CALLER GOES.** `passport_access`'s "Teachers can insert access for approved, matching institutions" and "Teachers can reactivate their own revoked access" (live definitions: `0100`) both gate on `passport_institution_links.approved_by_parent = true`. `AddChildSheet` was their only real caller — the principal-driven `grant_passport_access()` is `SECURITY DEFINER` and bypasses ordinary RLS on `passport_access` entirely, so it never touched these policies. Deleting `AddChildSheet` (PRD 3 Stage 2) makes both policies permanently unreachable by any real flow. Dead, not wrong — not urgent to remove, but nothing else in the schema will ever surface that fact; the next person auditing `approved_by_parent`'s remaining live dependents would otherwise have to work this out from scratch.

- **BEFORE TEARING DOWN ANY FIXTURE, GREP THE ADVERSARIAL SUITE FOR ITS INSTITUTION CODE AND ACCOUNT EMAILS.** A fixture that looks like leaked debris can still be a live dependency: `ZZFIXTURESTAGE1` was correctly identified as leaked test data and correctly torn down (`scripts/dev/teardown.mjs`) — but `CHECK W`'s own `W11c` referenced that exact institution as its one live example of a `'grandfathered'` `approval_source` value (the signature of `0101`'s one-time historical backfill, which no production path can ever reproduce), and nothing checked for that reference before deleting it. One command — `grep -rn "<institution_code>\|<email-prefix>" scripts/incident-log-test/adversarial-verify.mjs` — would have caught it before the deletion instead of after, in a full-suite run's failure list.

- **`principal_handovers` HAS NO CASCADE ON ITS `institution_staff` FOREIGN KEYS — DELIBERATELY — AND A RAW TEARDOWN DELETE WILL HIT IT.** A fixture that exercises `hand_over_principal()` (real handover records, not just the staff rows themselves) cannot delete those staff rows with a plain `institution_staff` delete afterward — `principal_handovers` (migration `0102`) references `institution_staff.id` from FOUR columns, none of them `on delete cascade`, matching this schema's own audit-trail pattern of never letting a legal/history record silently lose its referent: `principal_handovers_predecessor_institution_staff_id_fkey` (not null, always set), `principal_handovers_successor_old_institution_staff_id_fkey` (not null, always set), `principal_handovers_successor_new_institution_staff_id_fkey` (not null, always set), and `principal_handovers_predecessor_new_institution_staff_id_fkey` (nullable, set only when `outcome = 'staying'`). Hit for real tearing down PRD 5 Stage 2's handover-test fixture — confirmed live, not guessed, via the actual Postgres error on the first constraint. The fix: delete the fixture's own `principal_handovers` rows first, then the `institution_staff` rows, same ordering `scripts/dev/teardown.mjs` already uses for every other non-cascading audit table. This is the audit trail working as designed, not a bug to route around.

- **FIXTURES AND NEW LIFECYCLE STATE.** When a migration adds a state a production path is responsible for setting, existing fixtures WILL break — and that is correct. Fix them by driving the real production path (the RPC, as a real signed-in session), never by setting the column directly in a service-role insert. A fixture that sets such a column directly is testing the database's shape, not the system's behaviour. This happened for real when `0100_institution_join_approval.sql` made `class_teacher`/`sna` joins pending by default: every fixture across the suite that inserted staff via service role had encoded "row exists = active," correctly went false, and 353 checks failed loudly rather than passing against a state production no longer produces — the opposite outcome to the earlier `status: "awaiting_attestation"` incident (a fixture hand-setting a column production derives, which stayed green while masking a real bug through 180 checks), from the identical root cause. The fix in both cases is the same: call the real RPC (`approve_staff_join()`, as the principal's own session), never assign the column. One more thing worth naming from this repair pass: fixing ~6 fixture blocks this way exercised `approve_staff_join()`'s happy path repeatedly as a side effect, but not one existing check asserts on that RPC's *own* correctness (authorization, refusing a non-principal or wrong-institution caller, refusing double-approval) — every downstream check only needed the state it produces to be right, not the RPC's own behavior verified. That verification doesn't exist yet anywhere in the suite; a fixture-repair pass fixing fixtures is not the same claim as Step 2 writing real coverage for a migration's own new surface, and shouldn't be mistaken for it.

- **The adversarial suite tests the database, not the journey — it never renders or drives a UI.** Every check calls the Supabase client directly with a real JWT; none of them touch a React component, a redirect, or conditional rendering. A check whose NAME describes a user-facing outcome ("a deactivated person rejoining...") can pass while the actual page a person uses is broken, if the bug lives entirely in client-side routing/gating logic rather than in RLS/an RPC/a trigger — the class of thing this suite is built to catch. This happened for real: `join-institution/page.tsx`'s `checkExisting()` had no `deactivated_at` filter, silently redirecting a deactivated person back to their old dashboard instead of the join form, while CHECK V10's own direct-INSERT check kept passing, honestly proving the database would accept a legitimate rejoin — a true claim, just narrower than the check's name promised. Found only by hand, not by the suite. When a check's claim is about what a user would *experience* rather than what the database *permits*, write it against the CLIENT'S OWN QUERY SHAPE, file:line-matched to the component that gates the real journey — not a proxy for it, the literal same filter — so a regression in that client code fails the check the same way a regression in an RLS policy would.

- **COVERAGE GAPS ARE NOT WRONG-REASON PASSES.** A wrong-reason pass is a check that asserts the wrong thing. A coverage gap is a mechanism with no check at all, exercised only as a side effect of other fixtures. `approve_staff_join()` had six fixtures depending on its happy path and zero checks on its guards. When a new RPC is added, ask what asserts its REFUSALS — not whether anything uses it.

- **THE SUITE ENCODES OUR BELIEFS, NOT TRUTH.** Adversarial checks catch contradictions between code and spec. They cannot catch an error IN the spec — a check written from a wrong assumption will confirm the bug. `0105` tightened an edit policy per instruction; the accompanying check asserted the same wrong thing and passed. When a check is written from a stated requirement rather than from observed behaviour, ask what would have to be true for the requirement itself to be wrong.

- **A CHECK CAN ENCODE A BUG AS A SPEC.** A different failure from a wrong-reason pass: a wrong-reason pass asserts the wrong thing while believing it's testing something else; this is a check that asserts EXACTLY what it claims, faithfully and correctly — and what it claims is itself wrong. CHECK C, named "SNA can stamp but cannot complete stage two or sign off," asserted that limitation as a PASS. It was telling the truth about the database's own behaviour the whole time — `owning_teacher_id = null` for an SNA-created incident, silently unwritable by anyone, forever (migration 0159's own bug). The check wasn't lying; the thing it was faithfully proving was the defect. When a check's NAME describes a limitation rather than a guarantee — "cannot", "is refused", "has no" used about a *capability* rather than an *unauthorized actor* — ask whether the limitation is the one actually intended, not just whether the check passes. A second instance found in the same pass: `claim_incident()` existed as the designed recovery path for exactly this scenario, with zero client callers, ever — an escape hatch built and never wired up, which is how the bug shipped invisibly for as long as it did.

- **WHEN ACCESS OR AUTHORITY IS GRANTED, TEST THE DESTINATION.** Two gaps found in one session: an ownership transfer whose recipient could not edit what they received (`AA-8` proved the transfer record but never asked whether the new owner could act on it — `can_own_incident()` never recognised a principal as eligible), and an SNA assignment with no route for the assignee to reach the child (`assign_sna_to_child()` has been live since Stage 2; `/sna/passports` only ever queried `passport_access` directly, never `has_sna_access()` or any of the other access sources — the suite proved the grant, nothing asked whether the person could get to it). In both cases the grant was correct and adversarially proven. Granting access and being able to USE it are separate claims, and the suite only ever tests the first — it never renders a route. For every new access source, ask which screen surfaces it, and prove that screen queries the right thing.

  **Two more instances of the identical shape, found live on the deployed app during Stage 3's own browser-verification pass, in the SAME session that had just fixed `/sna/passports`** — a reminder that fixing one occurrence doesn't inoculate the neighbouring surfaces: (1) `useSnaChildren.ts`'s merged list correctly resolved a covering SNA's class-wide roster, but did it by reading `class_children` directly — a table whose own SELECT policy (0104) is deliberately narrower than `has_sna_access()`, current class teacher or principal only. The list query returned nothing, RLS-silent, for exactly the covering SNA it was built for; fixed with a narrow SECURITY DEFINER RPC (`get_temporary_access_covered_children()`), not a widening of that policy. (2) The list itself, once fixed, linked into `/sna/passport/[passportId]` — whose OWN access guard had never been touched, still a direct `passport_access`-only read predating this stage, refusing the exact child the list had just shown as accessible ("we couldn't find this classroom profile"). Fixed by replacing that guard with a call to `has_sna_access()` itself, so the guard and the underlying RLS can never independently drift again. Generalised: a fix at one layer (the list's own query) does not imply the layers it reads from or links to were fixed too — each hop in "grant → list → detail → write" is a separate claim, and needs testing separately. A THIRD component from the same stage (`TemporaryAccessBanner`) turned out to have been built, working, and never imported anywhere at all — found only by trying to see it live, not by any code-level reasoning; a component's own correctness proves nothing about whether it was ever wired in.

  **A separate, unrelated tooling trap surfaced during the same pass, worth recording so it isn't mistaken for a real bug again**: Next.js's client-side Router Cache can keep serving a stale RSC payload for a route across repeated `location.href` reassignments and even explicit hard reloads WITHIN THE SAME BROWSER TAB, even after the underlying deploy has genuinely gone green (confirmed via response headers showing `x-vercel-cache: MISS`, and the served JS bundle itself containing the new code, searched for directly). It looked exactly like the fix hadn't shipped. Closing the tab and opening a fresh one cleared it. If a just-deployed fix doesn't seem to be taking effect in browser verification despite the deploy SHA checking out, try a genuinely fresh tab before concluding the fix is wrong.

- **QUERY LIVE STATE, NOT AN EVENT LOG, FOR ANYTHING ACTIONABLE.** `school_notices` is append-only with nothing keeping it in sync with the tables holding current state. `'attestation_withdrawn'` fires once and knows nothing about a later re-attestation; `'incident_parent_call'` knows nothing about `mark_parent_called()`. A dashboard built on notices shows resolved items as outstanding until someone clicks them away — a persistent flag standing in for a live fact. Notices are a record of what happened; they are not a source of what is currently true. One extra join, and it cannot drift. Decided during PRD 2 Stage 7's own dashboard recon, weighing `school_notices` against querying `incident_children`/`incident_attestations` directly for "restraints needing a parent call" and "withdrawn attestations institution-wide" — neither built on notices, both on live state.

- **A PRINCIPAL MAY SEE AND SORT BY WHO LOGGED AN INCIDENT — THE PRD 4 STAGE 3 RULE AGAINST THIS WAS WRONG, OVERRULED.** `principal/incidents/page.tsx` originally shipped with "no Reporter/author column and no sortable 'who logged this' axis," reasoning that staff should appear as authors within a record (the countersign report), never as a column to sort by. Overruled by Daniel directly: a principal seeing one teacher's name recur across incidents is identifying where support is needed, not ranking people — that's the product's actual purpose, and withholding it made the tool worse at its own job. The distinction that matters, and the one to preserve going forward: identification and sorting are fine; what must never be built is anything that presents this as a performance metric — a league table, a score, a ranking framed as evaluation. A sortable column naming who logged an incident is fine. A count, a leaderboard, or copy implying comparison between staff is not, and needs its own conversation before it gets built, not a silent extension of this decision.

- **THE SUPPORT BUTTON IS THE ONE DELIBERATE RED IN THIS PRODUCT.** The nav icon and the raised alert are red because a teacher presses it when a situation is out of hand and they cannot manage alone. Golden Brown — the app's attention colour — reads as an outstanding task, which this is not. It must NOT use the Calm pair, which signals a distressed child rather than a call for adults. Its own token, used nowhere else (`--color-support-red-raw` / `--color-brand-support-red`, `#D7263D`, `src/app/globals.css`). The no-semantic-red rule still holds everywhere else.

- **A DELIBERATE BREAK IN VISUAL CONTINUITY IS NOT THE SAME AS A BROKEN PAGE — THE TEST IS WHETHER CONTENT AND STYLE CHANGE TOGETHER.** The consent/agreement screens (`src/components/consent/`) were rebuilt medtech-sharp — Inter, near-monochrome, hairline rules, a content-width pill button — deliberately unlike the rest of the app's warm, rounded, Baloo-2-and-card language, including dropping the brand icon entirely (kept only a small grey text wordmark) once it turned out that icon itself contains Golden Brown fills that would have broken the screens' own stricter colour rule. Checked live, arriving from the login screen: it reads as a different kind of moment, not a different (or broken) app. The reason, worth reusing whenever a screen is deliberately styled off-system: a broken or half-loaded page is FAMILIAR content in the WRONG style (a login form in the wrong font); this is UNMISTAKABLY NEW content — legal-feeling ticks and "BEFORE YOU START" rather than an email/password field — arriving in a new style, AT THE SAME MOMENT. Content and style shifting together reads as intentional; style shifting alone, or shifting only partway (some elements sharp, others still rounded), is what would have read as a bug. The class-management redesign will face the identical question — apply this same test, not a fresh gut check: does the new style arrive WITH new content, or is it grafted onto the same content the rest of the app already shows the same way.

# Frontend layout gotchas

- **A CLASS THAT LOOKS RIGHT AND DOES NOTHING IS INVISIBLE TO A GREP-BASED SWEEP. MEASURE WITH `getBoundingClientRect()`, DON'T GREP FOR CLASSES.** Two prior desktop-width sweeps on the principal track both missed real stretched elements. The reason: `w-full lg:w-auto` — the correct, established pattern for "full width on mobile, content-width on desktop" — was already present on ten buttons/links and doing nothing on two of them. A grep for the class found it and called it fixed; nobody had actually measured the rendered width.

  **The real mechanism, confirmed live by forcing styles via `el.style.setProperty(..., 'important')` and watching what actually changed the rendered width — not reasoned from the class list, which gave a WRONG answer on the first pass**: `<button>` elements get shrink-to-fit sizing for `width: auto` from the browser's own form-control rendering rules, regardless of `display: block` — so `block w-full lg:w-auto` on a `<button>` works exactly as intended (confirmed on `School`'s own "Log out" and `ChildDetail`'s "Revoke access", both correctly content-width). `<Link>`/`<a>` elements get NO such exception — an ordinary block-level anchor with `width: auto` fills its containing block, full stop, which is the standard CSS2.1 block-box algorithm. `lg:w-auto` alone is silently inert on a `<Link>`; the fix is `lg:inline-block` (or another shrink-to-fit display value) alongside it. Two real instances fixed this way: `principal/passports/enrol/page.tsx`'s "Cancel" and `ReviewSection.tsx`'s locked-FBA "Save as PDF" link — both `<Link>`, both genuinely stretched (992px / full width) despite already carrying `lg:w-auto`.

  **The first version of this exact entry was itself wrong**, and is worth recording as the reason to keep verifying rather than stopping at a plausible-sounding explanation: the first theory (from one live measurement of a broken `<Link>` and a lone code-read of a working `<button>`) was "`width: auto` is inert on any `display: block` element, only inline-block/flex items shrink." That's a coherent-sounding CSS claim, and it was accepted and nearly written down before a second live measurement (forcing `width: auto` directly via inline `!important` on a "broken" `<button>` — no effect, it was already content-width) disproved it. The tag (form control vs. anchor) was the actual variable, not `display`. Don't let a theory that merely explains the one example you already found stand in for actually testing it against a second one.

- **`min-width: auto` IS THE DEFAULT ON A FLEX ITEM, AND IT DOESN'T ANNOUNCE ITSELF UNTIL SOME CHILD IS WIDE ENOUGH TO HIT IT.** A flex item refuses to shrink below its own content's intrinsic width unless given `min-w-0` explicitly — this has already bitten `principal/layout.tsx` and `clinician/layout.tsx` (their own content divs, fixed pre-emptively) and, found in this same pass, `ChildDetail.tsx`'s and `ClinicalFileDetail.tsx`'s own tab-content pane (`<div className="flex-1 px-4 py-4">` / `<main className="flex flex-1 flex-col gap-4 px-4 py-4">`, both missing `min-w-0`, both copied from the same original vertical-tab-rail pattern).
